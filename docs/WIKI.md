# Azazel

Azazel is a deterministic build-model layer for Zig. CUE validates project
intent, Azazel emits typed Zig build data, and `std.Build` remains the executor.
The production support contract lives in [`PRODUCTION.md`](PRODUCTION.md).

## Contents

The site navigation covers the production pipeline, schema, code generation,
examples, editor tooling, real-project corpus, troubleshooting, and file
reference.

## The problem

Zig makes its build system programmable, which is powerful but can mix project
configuration with version-specific `std.Build` compatibility code. Azazel
separates those responsibilities.

`project.cue` says what the project contains. `schema.cue` constrains that model.
`export.cue` resolves the public build graph. `gen_build_spec.sh` emits typed Zig
source. `build.zig` translates the result onto the supported Zig build APIs.

The result is a stable, machine-readable project model that can be validated,
inspected, diffed, consumed by tooling, and replayed across supported Zig lanes.
Azazel does not replace Zig as the build executor; it is a configuration/IR and
compatibility layer over it.

## The pipeline

```text
project.cue
    |
schema.cue + export.cue
    |  cue export -e build
    v
resolved model
    |  gen_build_spec.sh
    v
build_spec.zig
    |  comptime import
    v
build.zig / std.Build
    |
    v
zig-out/
```

The canonical path is:

```sh
python3 azazel check
python3 azazel gen
python3 azazel build
zig build test --summary all
```

`azazel gen` delegates to `gen_build_spec.sh`; there is one generator
implementation. `build_spec.zig` is generated and gitignored. Generation is
memoized, while CI removes the memoization stamp before its second pass so the
determinism check performs a real regeneration.

## Prerequisites

The production CI matrix covers Zig 0.14.1, 0.15.2, and 0.16.0 with CUE v0.16.0
and Python 3. Zig 0.17 can be described for development/corpus work but is not a
stable release lane while that toolchain is moving.

The hosted macOS smoke test uses Zig 0.16.0. Zig 0.15.2 is covered on Linux; the
current GitHub macOS 26 arm64 image cannot link that Zig version's build runner,
so that host/toolchain combination is not advertised as supported.

## Installation

For this repository:

```sh
git clone https://github.com/godofecht/azazel.git
cd azazel
./setup.sh --check-only
python3 azazel check
python3 azazel build
```

Azazel is pre-1.0. Production consumers should pin the exact revision or release
they test in CI and upgrade deliberately. Moving from the current vendored
integration shape to a centrally versioned consumer dependency is tracked as
production-adoption work.

## Quickstart (5 minutes)

Declare a module and executable:

```cue
package build

core: #Module & {
    kind: "module"
    root: "src/core.zig"
}

app: #Module & {
    kind:    "exe"
    root:    "src/main.zig"
    deps:    ["core"]
    profile: "release"
}
```

Export them from `export.cue`:

```cue
_modules: {
    "core": core
    "app":  app
}
```

Then:

```sh
python3 azazel check
python3 azazel gen
python3 azazel build
python3 azazel info
```

Normal Zig build arguments can be forwarded through `azazel build`.

## Schema reference

The authoritative type definitions are in [`../schema.cue`](../schema.cue).
A feature is considered implemented only when it survives schema validation,
CUE export, generated spec, and Zig execution.

### Module fields

| Field | Purpose | Default |
|---|---|---|
| `kind` | `exe`, `static`, `shared`, or `module` | required |
| `root` | root Zig source | required |
| `artifact_name` | produced name independent of graph/import key | module key |
| `deps` | internal module dependencies | `[]` |
| `profile` | `debug` or `release` | `debug` |
| `link` | `abi` or `import` consumption | `abi` |
| `pre`, `post` | explicit argv build commands | `[]` |
| `install_dirs` | install/resource directory staging | `[]` |
| `pkg_library_paths` | package-provided library search paths | `[]` |
| `pkg_imports` | imported Zig package modules | `[]` |
| `pkg_artifacts` | linked package artifacts | `[]` |
| `build_options` | named user-selectable typed options | `[]` |
| `option_values` | fixed typed values injected into options | `[]` |
| `gen_imports` | Zig modules generated by host tools | `[]` |
| `generated` | outputs of top-level `generated` steps this module consumes | `[]` |
| `build_options_import` | options-module import name | `build-options` |
| `native` | C/C++ sources, includes, objects, libs, frameworks | `{}` |

A `shared` target is always ABI-linked. A `module` target is always import-only
and produces no standalone artifact.

### Import and ABI edges

`link: "import"` uses Zig module import semantics and avoids a separate artifact
for that dependency. `link: "abi"` keeps an independent compile artifact and
links it. Large projects can combine the two into clusters: import-connected
internals with ABI boundaries between clusters.

### Toolchains and profiles

Projects can declare accepted Zig minor-version lanes and a preferred lane. The
generated build rejects a compiler outside the declared set before doing real
work. `debug` resolves to Zig `Debug`; `release` resolves to `ReleaseFast`.

### Native build metadata

`native` can describe C sources, include/system-include directories, library
paths, object files, system libraries, pkg-config libraries, Apple frameworks,
and libc/libc++ linkage. `native` says what to link. Whether the machine has
those things is declared separately in `system_deps`.

### System dependencies

`system_deps` is a top-level list of things the machine must provide. It is
checked before any artifact compiles.

```cue
system_deps: [
    {name: "wayland-scanner", kind: "tool", hint: "part of the wayland development package"},
    {name: "wlroots-0.20", kind: "pkg_config"},
    {name: "xkbcommon", kind: "pkg_config", min_version: "1.5"},
    {name: "ws2_32", kind: "library", os: ["windows"]},
    {name: "Cocoa", kind: "framework", os: ["macos"]},
    {name: "zlib.h", kind: "header"},
    {name: "vendor/include", kind: "include_dir"},
]
```

| Kind | Requirement | Probe |
|---|---|---|
| `tool` | a program on `PATH` | `std.Build.findProgram` |
| `pkg_config` | a library known to pkg-config | `pkg-config --exists`, with `--atleast-version` when `min_version` is set |
| `library` | a system library | links a one-line C program with `zig cc -l<name>` |
| `framework` | an Apple framework | links the same program with `zig cc -framework <name>` |
| `header` | a C header | compiles `#include <name>` with `zig cc`, searching every declared `include_dir` |
| `include_dir` | a directory, relative to the project root or absolute | checked for existence |

`os` limits a requirement to the listed operating systems: `linux`, `macos`,
`windows`, `freebsd`, `netbsd`, `openbsd`. A `tool` is matched against the host.
Every other kind is matched against the build target. An empty list means every
platform. `hint` is printed next to a missing requirement.

The generated build exposes the checks as a `doctor` step. Every artifact and
the install step depend on it.

```sh
python3 azazel doctor   # validate, generate, then run `zig build doctor`
zig build doctor        # the same checks, without the CLI
zig build               # runs the checks first and stops if one fails
```

A missing requirement looks like this:

```text
error: missing system dependency: tool wayland-scanner (part of the wayland development package): not found on PATH
+- system dependency: pkg-config library wlroots-0.20 failure
```

Header, library and framework probes run only when the target is the host.
When cross-compiling they are skipped and the compiler reports them.

`system_deps` states what must be present. It links nothing. Linking stays in
each module's `native` block.

### Generated files

`generated` is a top-level map of build steps that produce files. A module
names the outputs it consumes. The generator runs before that module compiles,
and reruns when one of its declared inputs changes.

```cue
// A Zig host tool, compiled and run. Its output becomes an importable module.
generated: version_data: {
    tool: {root: "src/tools/config_gen.zig", name: "config_gen"}
    args: [
        {kind: "literal", value: "--generate-version-data"},
        {kind: "input_file", value: "src/Config.zig"},
        {kind: "output_file", value: "version_data.zig"},
    ]
    outputs: [{name: "version_data.zig"}]
}

// A program on PATH. One run writes a C source and its header.
generated: xdg_shell: {
    command: ["wayland-scanner", "private-code"]
    args: [
        {kind: "input_file", value: "protocol/xdg-shell.xml"},
        {kind: "output_file", value: "xdg-shell.c"},
    ]
    outputs: [{name: "xdg-shell.c"}]
}

// A filter: stdin in, stdout captured, result installed.
generated: manpage: {
    command: ["scdoc"]
    stdin: "doc/tool.1.scd"
    stdout: "tool.1"
    outputs: [{name: "tool.1", install: "share/man/man1/tool.1"}]
}

// A file a build.zig.zon dependency generates and exports.
generated: unicode_tables: {
    package: {
        package: "uucode"
        named_path: "tables.zig"
        args: [{name: "fields", kind: "string_list", value: ["east_asian_width"]}]
    }
    outputs: [{name: "tables.zig", install: "share/tables.zig"}]
}

app: #Module & {
    kind: "exe"
    root: "src/main.zig"
    generated: [
        {from: "version_data", output: "version_data.zig", as: "import", alias: "version_data"},
        {from: "xdg_shell", output: "xdg-shell.c", as: "c_source"},
        {from: "unicode_tables", output: "tables.zig", as: "embed", alias: "tables"},
    ]
}
```

Exactly one producer is set per step:

| Producer | Runs |
|---|---|
| `tool` | a Zig source file from the project, compiled for the host |
| `command` | a program on `PATH`; declare it in `system_deps` as well |
| `package` | nothing itself: it takes a path the dependency exports with `addNamedLazyPath` |

`args` are passed in order. `literal` is passed as written. `input_file` is a
project path and a tracked input. `output_file` names a file the generator
writes; the build picks the real location and passes it. Every `output_file`
and the `stdout` capture must appear in `outputs`, and every output must be
produced by one of them. The generator rejects a mismatch.

A module consumes an output in one of four ways:

| `as` | Effect |
|---|---|
| `import` | the file is a Zig module, reached with `@import("<alias>")` |
| `embed` | any file, reached with `@embedFile("<alias>")` |
| `c_source` | compiled into the module as a C source |
| `include` | the output's directory joins the module's C include path |

An output with `install` is copied under the install prefix. `zig build
generate` produces every declared output without compiling a module.

`build_spec.zig` lists each step with its producer, arguments and outputs, so
the output names and install paths are explicit data. A `package` generator
must pass the same `args` and `optimize` as the module that imports that
package. They then share one dependency instance and the
generator runs once.

On Zig 0.14 and 0.15 a captured `stdout` file is named `stdout` on disk, so it
has no extension. Consume it with `embed` or `install` on those lanes.

`gen_imports` on a module is the older, narrower form: one host tool whose
output is imported by that module only.

### Subprojects and target slices

`subprojects` is a top-level map of nested packages. Each one records a
package-local root and where its artifacts install. A module joins a subproject
with `subproject`.

```cue
subprojects: {
    danzig:      {path: "src/danzig"}
    danzig_gain: {path: "examples/danzig-gain", output_dir: "examples/danzig-gain"}
}

danzig_gain: #Module & {
    kind: "shared"
    subproject: "danzig_gain"
    root: "examples/danzig-gain/root.zig"
    deps: ["danzig"]
}
```

`path` is relative to the repository root. It has no `..` and no trailing
slash. `output_dir` is relative to the install prefix. When it is set, the
subproject's executables install under `<output_dir>/bin` and its libraries
under `<output_dir>/lib`. A subproject whose path lies under another
subproject's path is a nested workspace.

A module's `root` stays relative to the repository root and must lie under its
subproject's `path`. `azazel check` and the generator both reject a module
outside its subproject, an unknown subproject, a missing directory, two
subprojects with one path, and a path that escapes the repository. Every
message names the subproject it concerns.

Each module has a target path. It is `<subproject path>/<module name>`, or the
module name for a module of the repository root. A slice is a glob over target
paths and subproject paths.

| Glob | Matches |
|---|---|
| `*` | any run of characters except `/` |
| `?` | one character except `/` |
| `**` | any run of characters including `/`; `**/` also matches no segment |

```sh
python3 azazel targets                          # every target path
python3 azazel targets --slice 'examples/*'     # what a slice selects
python3 azazel build --slice 'examples/*'       # build and install only those
python3 azazel build --subproject danzig_gain   # select a subproject by name
zig build subproject-danzig_gain                # the same through a generated step
zig build -Dslice='examples/*' -Dsubproject=danzig   # both options repeat
```

Only the selected modules install. A selected module still builds the modules
it depends on, because linking needs them, and the install step skips the rest.
A slice or subproject name that matches nothing fails before Zig compiles
anything, and the message lists the target paths that exist. When a selected
build fails, `azazel build` names the subproject paths it was building.

The glob matcher exists twice, in `compat.zig` for `build.zig` and in
`tools/workspace.py` for the CLI and the corpus. Both read
`tools/glob_cases.txt` in their tests.

### Packages and build.zig.zon

`packages` declares the project's `build.zig.zon` dependencies. The map name is
the dependency alias: the name `build.zig.zon` uses and the name modules refer
to in `pkg_imports`, `pkg_artifacts` and `pkg_library_paths`.

```cue
packages: {
    zigimg: {
        url:  "git+https://github.com/zigimg/zigimg#d695acd97c02e57bb151e8f659d1280f5cd6ca70"
        hash: "zigimg-0.1.0-8_eo2oyaFwBZwJpmqPkCfVXWBrHcqbYwmrp1I6bTD3lI"
    }
    uucode: {
        url:  "git+https://github.com/jacobsandlund/uucode#2826a37a4562284fdacd8fa029d49509cc9bffcd"
        hash: "uucode-0.2.0-ZZjBPlK5VADj7fdoq7G8LIHzD5o6FSkcBXXrRWr4jnrA"
        lazy: true
    }
    local_helper: path: "vendor/helper"
}

app: #Module & {
    kind: "exe"
    root: "src/main.zig"
    pkg_imports: [{alias: "img", package: "zigimg", module: "zigimg"}]
}
```

`alias` in `pkg_imports` is the `@import` name inside the module. It can differ
from both the package alias and the module name the package exports.

A package marked `lazy` is resolved with `lazyDependency`. Zig fetches it on
first use and configures the build a second time, so a lazy package costs
nothing until a module needs it.

`build.zig.zon` stays a real file that Zig reads. The CLI keeps its
`.dependencies` in step with `packages`:

```sh
python3 azazel zon check                  # list every difference
python3 azazel zon write                  # rewrite .dependencies from packages
python3 azazel zon import path/to/build.zig.zon   # print a packages block for another manifest
```

`zon write` replaces only the `.dependencies` value. The name, version,
fingerprint, paths and comments elsewhere in the file are left alone. `zon
import` is the way in from an existing project: it reads the upstream manifest
and prints the matching `packages` declaration.

`azazel check` fails when a module names a package that `packages` does not
declare, when a package has a url without a hash, and when `build.zig.zon`
disagrees with `packages`.

### Dependency options

A dependency's build function takes options through `b.option`. A project
passes them with `args` on a `pkg_imports` entry, a `pkg_artifacts` entry or a
`generated` package. Each option has a `name`, a `kind` and a `value`.

| Kind | Value | Zig argument |
|---|---|---|
| `bool` | `true` or `false` | `.with_implot = true` |
| `int` | a 64-bit integer | `.buffer_pool_size = 256` |
| `string` | text | `.label = @as([]const u8, "x")` |
| `string_list` | a list of text | `.fields = @as([]const []const u8, &.{ "a", "b" })` |
| `enum` | a tag name | `.backend = .glfw_wgpu` |
| `target` | `"forward"` or a triple such as `"aarch64-linux-gnu"` | `.target = target` |
| `optimize` | `"forward"` or `Debug`, `ReleaseSafe`, `ReleaseFast`, `ReleaseSmall` | `.optimize = optimize` |

```cue
packages: zgui: path: "deps/zgui"

app: #Module & {
    kind: "exe"
    root: "src/main.zig"
    pkg_imports: [{
        alias: "zgui"
        package: "zgui"
        module: "root"
        args: [
            {name: "backend", kind: "enum", value: "glfw_wgpu"},
            {name: "with_implot", kind: "bool", value: true},
        ]
    }]
}
```

The generator writes the call out as Zig source in `build_spec.zig`, one
function per distinct package and option list:

```zig
fn dep_136cbad83146(b: *std.Build, target: std.Build.ResolvedTarget, optimize: std.builtin.OptimizeMode) ?*std.Build.Dependency {
    return b.dependency("zgui", .{ .@"target" = target, .@"optimize" = optimize, .@"backend" = .@"glfw_wgpu", .@"with_implot" = true });
}
```

Zig reads dependency options from the field names and types of that struct, so
the call has to exist as source. Option names and enum tags become field names
and enum literals the compiler checks, quoted so a name such as `with-odd-name`
is valid. `build.zig` holds no option names. It calls the function the spec
gives each use, and it resolves a `lazy` package with `lazyDependency`.

`pass_target` and `pass_optimize` forward the module's own target and optimize
mode as the options `target` and `optimize`. Turn one off to pass your own
through `args`. Passing a name twice, including `target` while `pass_target` is
on, is an error.

Checks run in this order:

1. CUE rejects a value that does not fit its kind: a string for a bool, a
   float for an int, an unknown `kind`.
2. The generator rejects duplicate names, a bad target triple, an optimize mode
   that does not exist, and an int outside 64 bits.
3. `azazel check` reads the dependency's `build.zig` when it is on disk, as it
   is for a `path` package and for a fetched package in the Zig cache. It lists
   what `b.option`, `standardTargetOptions` and `standardOptimizeOption`
   declare. Each arg must name a declared option, the kind must match the
   declared type, and an enum tag must be one the option's enum defines. A
   dependency that declares no options is not checked, because it may read them
   through helpers the scan cannot follow. Set `unchecked: true` on an arg to
   skip the comparison for that option.

```text
error: module 'app' imports package 'zgui': option 'bakend' for package 'zgui' is not declared by zgui/build.zig (declared: backend, optimize, shared, target, with_implot); did you mean 'backend'?
error: module 'app' imports package 'zgui': option 'backend' for package 'zgui' is given tag 'glfw_wgpuu', which its enum does not define (tags: no_backend, glfw_wgpu, glfw_opengl3; zgui/build.zig:27)
```

`python3 tools/dep_options.py path/to/build.zig` prints the options a build
script declares.

The earlier `backend` and `fields` fields on imports, artifacts and generated
packages are gone. Write `{name: "backend", kind: "enum", value: "..."}` and
`{name: "fields", kind: "string_list", value: [...]}` instead.

### Options, packages, and generated modules

Top-level options currently support bool, string, and `u32` values. Modules can
also receive fixed typed `option_values`, including optional 40-character commit
values.

`pkg_imports`, `pkg_artifacts`, and `pkg_library_paths` model real
`build.zig.zon` dependency surfaces. The options a dependency takes are
described under "Dependency options".

`gen_imports` models the common pattern of compiling a host tool, running it,
and importing the emitted Zig file through the build graph.

### `export.cue`

`project.cue` contains declarations; `export.cue` chooses which declarations
become the resolved build graph and projects every field the generator consumes.
The `_modules` map is the explicit export list. The canonical CLI verifies that
the complete module contract survived this stage, preventing schema features
from being silently dropped downstream.

## From build_spec.zig to build.zig

`build_spec.zig` contains typed constants for toolchain lanes, packages, options,
and modules. `build.zig` imports it at comptime, rejects unsupported Zig lanes,
creates `std.Build.Module` values, applies native/options/package/generated
metadata, creates only the artifacts that need independent compilation, wires
import or ABI edges, and attaches install/post-build steps.

This executor is where Zig-version API adaptation belongs. Keeping that logic
centralized is the main compatibility value Azazel offers consuming projects.

## Editor support

`ide/` contains VS Code and language-server experiments for CUE diagnostics,
completion, hover information, and dependency navigation. Editor tooling is not
a runtime dependency of the production build path and is currently outside the
production support contract.

## Huge project corpus

`tools/huge_corpus.py` pressure-tests Azazel against substantial Zig projects,
including ZLS, libxev, River, Mach, MicroZig, libvaxis, Capy, zig-gamedev,
TigerBeetle, and Ghostty.

The corpus deliberately distinguishes upstream build success from Azazel
replacement evidence. An upstream result runs the project's own `build.zig`; an
Azazel executable-parity result means a modeled target slice actually compiled
through the generated Azazel graph. Full-project parity is not claimed from a
successful slice.

A corpus repo can declare target slices, such as `samples/minimal_*` for
zig-gamedev and `port/*/*` for MicroZig. A run builds the selected directories
one at a time and reports the selected paths. See
[`HUGE_PROJECT_CORPUS.md`](HUGE_PROJECT_CORPUS.md) for the detailed matrix.

## Troubleshooting

### Missing exported fields

If `azazel check` reports missing fields, a schema/project capability was not
preserved by `export.cue`. Treat that as an Azazel pipeline bug.

### Unknown dependency or cycle

Every `deps` entry must name an exported module. `azazel check` rejects unknown
references, self-dependencies, and cycles before generation.

### Module declared but not built

Check `_modules` in `export.cue`; only explicitly exported declarations enter the
resolved graph.

### Unsupported Zig lane

Use a compiler in the project's declared lane set. Do not widen the declaration
until the project has actually been tested there.

### Package option is unsupported

Do not silently discard it. Model it explicitly with a real-project test, or use
the generic typed dependency-option work once it lands.

### Shared cache says the build is not cacheable

`cache_build.sh` exits with status 3 and lists a reason for each input the key
cannot name, such as a `post` command, a system library or an unmodeled build
argument. Run `python3 azazel cache-key --explain` to see the same list. Remove
the cause or build without the cache. See [`../CACHE.md`](../CACHE.md).
