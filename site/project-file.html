Project File

project.cue is the only file you edit. It declares your modules — what to build, from what source, with what dependencies and optimization level.

Module Fields

Every module is defined as a #Module struct with these fields:

FieldTypeRequiredDefaultDescription
kind"exe" | "static" | "shared"Yes—Output artifact type
rootstringYes—Path to root source file
deps[...string]No[]Names of modules this depends on
profile"debug" | "release"No"debug"Optimization profile

Minimal Example

The simplest valid project — a single executable with no dependencies, built in debug mode:

package build

app: #Module & {
    kind: "exe"
    root: "src/main.zig"
}

Three fields. The deps defaults to an empty list, profile defaults to "debug".

With Dependencies

A static library with an executable that links against it:

package build

core: #Module & {
    kind: "static"
    root: "src/core.zig"
}

app: #Module & {
    kind:    "exe"
    root:    "src/main.zig"
    deps:    ["core"]
    profile: "release"
}

app links against core at compile time. The "release" profile resolves to Zig's .ReleaseFast optimization mode. core inherits the default "debug" profile.

Note Dependencies are resolved by name — the string "core" in the deps array must match the key name of another module definition in the same file.

Output Types

"exe"

Produces a native executable binary. Installed to zig-out/bin/ automatically.

"static"

Produces a static library (.a). Available for linking by other modules via deps.

"shared"

Produces a shared/dynamic library (.so / .dylib / .dll). Linked at runtime.

Wiring Modules to Export

When you add or remove modules in project.cue, you must also update the _modules map in export.cue to match:

_modules: {
    "core": core
    "app":  app
}

This map is the single source of truth for what gets generated into build_spec.zig. Only modules listed here will be included in the build.

Important If you add a module to project.cue but forget to add it to export.cue, it will be validated but not included in the generated build spec.

Profile Behavior

ProfileZig OptimizeModeUse Case
"debug".DebugDevelopment — fast compilation, safety checks enabled
"release".ReleaseFastProduction — maximum performance, safety checks disabled

Each module can have its own profile. A common pattern is debug libraries with a release executable during development, and release everything for production.

Dependency Resolution

Understanding how dependencies work is critical to using Azazel effectively.

How deps are resolved

When you write deps: ["core"], here's what happens at each stage:

  1. CUE validation: CUE checks that "core" is a valid string. It does not check that a module named core exists — CUE only validates types, not cross-references.
  2. Codegen: The string "core" is emitted verbatim into build_spec.zig as part of the deps array.
  3. Zig build: build.zig looks up "core" in its hash map of compiled modules. If the name doesn't match any module, the build panics.
Important Dependency names are resolved by exact string match against module names. A typo in the deps array will only be caught at zig build time, not during CUE validation. Double-check your spelling.

Dependency ordering

You can define modules in any order in project.cue. Azazel's two-pass build engine handles forward references — a module can depend on a module that appears later in the file. This is unlike Makefiles, where order matters.

Circular dependencies

Circular dependencies (A depends on B, B depends on A) will cause zig build to fail. Zig's linker does not support circular library dependencies. If you need bidirectional communication between modules, refactor the shared interface into a third module.

Common Patterns

All-release production build

// Set every module to release
core: #Module & {
    kind:    "static"
    root:    "src/core.zig"
    profile: "release"
}

app: #Module & {
    kind:    "exe"
    root:    "src/main.zig"
    deps:    ["core"]
    profile: "release"
}

Debug library + release executable

// Safety checks in the library, max perf in the exe
core: #Module & {
    kind: "static"
    root: "src/core.zig"
    // profile defaults to "debug" — safety checks on
}

app: #Module & {
    kind:    "exe"
    root:    "src/main.zig"
    deps:    ["core"]
    profile: "release"
}

This catches bugs in library code (via Zig's safety checks) while still getting optimized executable performance.

Multiple executables sharing a library

// One library, many consumers
shared_lib: #Module & {
    kind:    "static"
    root:    "src/lib.zig"
    profile: "release"
}

tool_a: #Module & {
    kind: "exe"
    root: "src/tool_a.zig"
    deps: ["shared_lib"]
    profile: "release"
}

tool_b: #Module & {
    kind: "exe"
    root: "src/tool_b.zig"
    deps: ["shared_lib"]
    profile: "release"
}
