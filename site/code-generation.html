Code Generation

Azazel generates Zig source code — not JSON, not YAML, not any intermediate format. The build system never parses anything at runtime.

The Codegen Pipeline

The generation process has three distinct phases, each with a clear boundary:

Generated Output

For a project with core (static, debug) and app (exe, release), gen_build_spec.sh produces:

const std = @import("std");

pub const Kind = enum { exe, static, shared };

pub const Module = struct {
    name: []const u8,
    kind: Kind,
    root: []const u8,
    deps: []const []const u8,
    optimize: std.builtin.OptimizeMode,
};

pub const modules = [_]Module{
    .{
        .name = "core",
        .kind = .static,
        .root = "src/core.zig",
        .deps = &.{},
        .optimize = .Debug,
    },
    .{
        .name = "app",
        .kind = .exe,
        .root = "src/main.zig",
        .deps = &.{ "core" },
        .optimize = .ReleaseFast,
    },
};

This file is a compile-time constant array. build.zig imports it with @import("build_spec.zig") and iterates the array to create build steps. No parsing, no allocation, no error handling required.

Why Not JSON?

Zero Runtime Cost

No JSON parsing at build time. The module array exists as compile-time constants in the Zig binary.

Type Safety

Zig's compiler catches type mismatches in the generated spec. A malformed codegen output fails at compile time, not runtime.

No Dependencies

No std.json, no allocator, no error unions. The build script is simpler and more predictable.

Auditable

The generated file is human-readable Zig. You can inspect exactly what will be built before running zig build.

How the Script Works

gen_build_spec.sh is a thin pipeline:

  1. Runs cue export -e build to produce normalized JSON (internal only — never consumed by Zig)
  2. Pipes the JSON through a Python script that emits Zig source code
  3. Writes the result to build_spec.zig
Important JSON is used as an internal transport format between CUE and the codegen script — it never enters the Zig compilation pipeline. The Zig compiler only ever sees typed Zig source code.

Script Source Walkthrough

The complete gen_build_spec.sh is straightforward. Understanding it helps when debugging or extending the codegen:

#!/bin/sh
set -e
cd "$(dirname "$0")"

# Step 1: CUE exports the normalized build data as JSON
DATA=$(cue export -e build)

# Step 2: Write the Zig type definitions (static header)
cat > build_spec.zig <<'HEADER'
const std = @import("std");

pub const Kind = enum { exe, static, shared };

pub const Module = struct {
    name: []const u8,
    kind: Kind,
    root: []const u8,
    deps: []const []const u8,
    optimize: std.builtin.OptimizeMode,
};
HEADER

# Step 3: Generate the module array from CUE's JSON output
printf 'pub const modules = [_]Module{\n' >> build_spec.zig

echo "$DATA" | python3 -c "
import json, sys
data = json.load(sys.stdin)
for name, m in data['modules'].items():
    opt_map = {
        'Debug': '.Debug',
        'ReleaseFast': '.ReleaseFast',
        'ReleaseSafe': '.ReleaseSafe',
        'ReleaseSmall': '.ReleaseSmall'
    }
    deps = m.get('deps', [])
    deps_str = '&.{ ' + ', '.join(
        '\"' + d + '\"' for d in deps
    ) + ' }' if deps else '&.{}'
    print(f'''    .{{
        .name = \"{name}\",
        .kind = .{m['kind']},
        .root = \"{m['root']}\",
        .deps = {deps_str},
        .optimize = {opt_map[m['optimize']]},
    }},''')
" >> build_spec.zig

printf '};\n' >> build_spec.zig

Key design decisions in the script:

  • Static header: The Kind enum and Module struct are hardcoded — they match what build.zig expects. If you add a new kind, you update both.
  • Python for codegen: Python handles the JSON-to-Zig transformation because CUE doesn't have built-in Zig string templating. The Python is deliberately simple — a single comprehension loop.
  • No error handling: The script uses set -e to fail fast. If CUE validation fails, the script stops before writing any Zig.

The Zig Build Engine

The generated build_spec.zig is consumed by build.zig. Here's the complete build engine:

const std = @import("std");
const spec = @import("build_spec.zig");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});

    // Pass 1: Create all compile steps
    var built = std.StringHashMap(
        *std.Build.Step.Compile
    ).init(b.allocator);
    defer built.deinit();

    for (spec.modules) |m| {
        const step = switch (m.kind) {
            .exe => b.addExecutable(.{
                .name = m.name,
                .root_source_file = b.path(m.root),
                .optimize = m.optimize,
                .target = target,
            }),
            .static => b.addStaticLibrary(.{
                .name = m.name,
                .root_source_file = b.path(m.root),
                .optimize = m.optimize,
                .target = target,
            }),
            .shared => b.addSharedLibrary(.{
                .name = m.name,
                .root_source_file = b.path(m.root),
                .optimize = m.optimize,
                .target = target,
            }),
        };
        built.put(m.name, step) catch unreachable;
    }

    // Pass 2: Link dependencies and install
    for (spec.modules) |m| {
        const step = built.get(m.name).?;
        for (m.deps) |dep| {
            step.linkLibrary(built.get(dep).?);
        }
        if (m.kind == .exe) b.installArtifact(step);
    }
}

Why two passes? A module might depend on another module that appears later in the array. Pass 1 creates all steps first, Pass 2 links them. This decouples definition order from dependency order.

Why catch unreachable? The hash map allocation can only fail if the allocator runs out of memory. In a Zig build script, the allocator is the build system's arena — it doesn't run out. Using unreachable keeps the code clean.

Why .? on hash map lookups? If a dependency name doesn't match any module, this produces a clear panic with the failing assertion. In practice, if CUE validated successfully, all names will resolve.

Regenerating

Run the script whenever you change project.cue or export.cue:

./gen_build_spec.sh

build_spec.zig is gitignored — it is a generated build artifact, not a source file. You can safely delete it and regenerate at any time.

Relationship to Zaza

In the Zaza build system, this same codegen pattern can be extended to produce more complex build specifications — including C/C++ interop targets, WebAssembly outputs, and CMake integration modules. Azazel provides the minimal, principled core that Zaza's extended pipeline builds upon.
