Examples

Real-world project configurations demonstrating different build topologies — from single-file binaries to deep dependency trees with mixed library types. All examples are in the examples/ directory.

1. Minimal — Single Executable

The smallest valid Azazel project. One executable, no dependencies. The profile defaults to "debug" and deps defaults to [] — you don't need to specify either.

package build

app: #Module & {
    kind: "exe"
    root: "src/main.zig"
}

export.cue:

_modules: { "app": app }

What you get: A single binary at zig-out/bin/app, compiled with .Debug optimization (safety checks on, no optimization, fast compile).

When to use: Quick prototypes, scripts, learning projects, or any project where a single source file is the entire program.

2. Library + Executable

The default Azazel project. A static library contains shared logic, and an executable links against it. This is the most common pattern for any non-trivial Zig project.

package build

core: #Module & {
    kind: "static"
    root: "src/core.zig"
}

app: #Module & {
    kind:    "exe"
    root:    "src/main.zig"
    deps:    ["core"]
    profile: "release"
}

export.cue:

_modules: { "core": core, "app": app }

What you get: core is compiled as a .a static archive with debug optimization. app is compiled with .ReleaseFast and links against core. Only the executable is installed to zig-out/bin/.

Why mixed profiles? During development, you often want your library in debug mode (for safety checks and readable stack traces) while the main executable is release-optimized (for realistic performance testing). In production, you'd set both to "release".

3. Multi-Library — Shared + Static + Exe

Demonstrates mixed library types in a single project. This pattern is common when you need a dynamically-loadable library (for plugin hosts or FFI consumers) alongside statically-linked utility code.

package build

math: #Module & {
    kind:    "shared"
    root:    "src/math.zig"
    profile: "release"
}

utils: #Module & {
    kind: "static"
    root: "src/utils.zig"
}

app: #Module & {
    kind:    "exe"
    root:    "src/main.zig"
    deps:    ["math", "utils"]
    profile: "release"
}

export.cue:

_modules: { "math": math, "utils": utils, "app": app }

What you get: math produces a .dylib (macOS) / .so (Linux) / .dll (Windows). utils produces a .a archive. app links both — math dynamically, utils statically.

When to use: When part of your code needs to be loadable at runtime (e.g., a math kernel shared across multiple tools, or a library exposed to other languages via C ABI).

4. Microservice — Protocol + Two Services

A shared protocol library consumed by two independent service binaries. This models a real microservice architecture where multiple services share serialization logic, RPC definitions, or wire format code.

package build

protocol: #Module & {
    kind:    "static"
    root:    "src/protocol.zig"
    profile: "release"
}

gateway: #Module & {
    kind:    "exe"
    root:    "src/gateway.zig"
    deps:    ["protocol"]
    profile: "release"
}

worker: #Module & {
    kind:    "exe"
    root:    "src/worker.zig"
    deps:    ["protocol"]
    profile: "release"
}

export.cue:

_modules: { "protocol": protocol, "gateway": gateway, "worker": worker }

What you get: Two independent binaries (zig-out/bin/gateway and zig-out/bin/worker) that both link the same protocol library. Changes to protocol.zig are automatically reflected in both.

When to use: Microservice architectures, client/server pairs, or any project where multiple executables share common protocol, serialization, or data format code.

5. Game Engine — Deep Dependency Tree

A realistic game project with a layered architecture: low-level libraries feed into an engine core, which feeds into the game. This demonstrates how Azazel handles deep, multi-level dependency chains.

package build

renderer: #Module & {
    kind:    "static"
    root:    "src/renderer.zig"
    profile: "release"
}

audio: #Module & {
    kind:    "static"
    root:    "src/audio.zig"
    profile: "release"
}

physics: #Module & {
    kind:    "static"
    root:    "src/physics.zig"
    profile: "release"
}

engine: #Module & {
    kind:    "static"
    root:    "src/engine.zig"
    deps:    ["renderer", "audio", "physics"]
    profile: "release"
}

game: #Module & {
    kind:    "exe"
    root:    "src/game.zig"
    deps:    ["engine"]
    profile: "release"
}

export.cue:

_modules: {
    "renderer": renderer
    "audio":    audio
    "physics":  physics
    "engine":   engine
    "game":     game
}

What you get: Five modules compiled in dependency order. game only declares a dependency on engine, but transitively links renderer, audio, and physics through Zig's linkLibrary.

Key pattern: Azazel's two-pass build engine handles arbitrarily deep dependency trees. You declare direct dependencies only — transitive resolution is automatic. The foundation libraries can be developed and tested independently.

Note Dependencies in Azazel are direct, not transitive. game depends on engine, which depends on renderer/audio/physics. Zig's linker resolves the full chain. You don't need to list transitive deps in the deps array.

6. Plugin System — Host + Dynamic Plugins

A host application that loads shared library plugins at runtime. The plugins and host share a common interface definition compiled as a static library. This models audio plugin hosts, editor extensions, or any modular architecture.

package build

plugin_api: #Module & {
    kind:    "static"
    root:    "src/plugin_api.zig"
    profile: "release"
}

host: #Module & {
    kind:    "exe"
    root:    "src/host.zig"
    deps:    ["plugin_api"]
    profile: "release"
}

reverb: #Module & {
    kind:    "shared"
    root:    "src/plugins/reverb.zig"
    deps:    ["plugin_api"]
    profile: "release"
}

chorus: #Module & {
    kind:    "shared"
    root:    "src/plugins/chorus.zig"
    deps:    ["plugin_api"]
    profile: "release"
}

export.cue:

_modules: {
    "plugin_api": plugin_api
    "host":       host
    "reverb":     reverb
    "chorus":     chorus
}

What you get: One executable (host) and two shared libraries (reverb.dylib, chorus.dylib). Both the host and the plugins link against the same plugin_api static library, ensuring ABI compatibility. The host uses std.DynLib to load plugins at runtime.

Key pattern: Shared libraries for runtime-loadable modules. The static plugin_api defines the interface contract. Adding a new plugin is one module definition — the host doesn't need to be recompiled.

7. CLI Tool — Shared Core + Multiple Commands

A command-line tool with a shared core library and multiple sub-command executables. Each command is a separate binary that links the same core, following the BusyBox / Git multi-binary pattern.

package build

cli_core: #Module & {
    kind:    "static"
    root:    "src/cli_core.zig"
    profile: "release"
}

init: #Module & {
    kind:    "exe"
    root:    "src/cmd/init.zig"
    deps:    ["cli_core"]
    profile: "release"
}

build_cmd: #Module & {
    kind:    "exe"
    root:    "src/cmd/build.zig"
    deps:    ["cli_core"]
    profile: "release"
}

deploy: #Module & {
    kind:    "exe"
    root:    "src/cmd/deploy.zig"
    deps:    ["cli_core"]
    profile: "release"
}

export.cue:

_modules: {
    "cli_core":  cli_core
    "init":      init
    "build_cmd": build_cmd
    "deploy":    deploy
}

What you get: Three separate binaries (init, build_cmd, deploy) that all share argument parsing, config loading, and output formatting from cli_core. Each binary is small and focused.

When to use: CLI tools with distinct subcommands, dev toolchains, or any project where different entry points share infrastructure code. This pattern keeps binaries small and allows independent deployment of individual commands.

8. Layered Server — Data + Logic + API

A layered server architecture where each layer only depends on the layer below it. This enforces architectural boundaries at the build level — the API layer cannot accidentally import data layer internals.

package build

data: #Module & {
    kind:    "static"
    root:    "src/data.zig"
    profile: "release"
}

logic: #Module & {
    kind:    "static"
    root:    "src/logic.zig"
    deps:    ["data"]
    profile: "release"
}

server: #Module & {
    kind:    "exe"
    root:    "src/server.zig"
    deps:    ["logic"]
    profile: "release"
}

export.cue:

_modules: { "data": data, "logic": logic, "server": server }

What you get: A strict layered architecture enforced by the build system. server can only call into logic. logic can only call into data. If a developer tries to @import across layers, Zig will fail to resolve the module — the build system enforces the boundary.

Key insight: This is one of the most powerful patterns in Azazel. By expressing architectural layers as separate modules with explicit deps, you get compile-time enforcement of dependency rules. No linter or convention needed — it's structural.

Architectural enforcement Because each module has its own root source file and explicit dependency list, Zig's module system prevents illegal cross-layer imports at compile time. This is stronger than any linter — it's a build error, not a warning.

Using an Example

Step-by-step

  1. Copy the example's project.cue content into your project.cue
  2. Update the _modules map in export.cue to match
  3. Create the corresponding source files in src/ (even empty pub fn main() void {} stubs work)
  4. Validate: cue vet
  5. Generate: ./gen_build_spec.sh
  6. Build: zig build

Inspecting what will be built

Before generating, you can see exactly how CUE resolves your configuration:

cue export -e build

This outputs the fully normalized JSON with all defaults applied and all profiles resolved to their Zig optimization values.

Important When switching between examples, always update both project.cue and export.cue together. The _modules map in export.cue must list exactly the modules you've defined — no more, no less.
