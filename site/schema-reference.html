Schema Reference

schema.cue defines the complete type system. It enforces correctness at configuration time — before any Zig code is generated. You should rarely need to modify it.

Type Definitions

#Kind enum

The output artifact type for a module.

#Kind: "exe" | "static" | "shared"
ValueZig Build APIOutput
"exe"b.addExecutable()Native binary
"static"b.addStaticLibrary().a archive
"shared"b.addSharedLibrary().so / .dylib / .dll

#Profile enum

The optimization strategy applied to a module.

#Profile: "debug" | "release"
ValueZig OptimizeModeBehavior
"debug".DebugNo optimization, safety checks on, fast compile
"release".ReleaseFastMaximum optimization, safety checks off

#Module struct

The core type. Every build target is a #Module.

#Module: {
    kind:     #Kind
    root:     string
    deps:     [...string] | *[]
    profile:  #Profile | *"debug"
}

CUE's * operator marks default values. If deps is omitted, it defaults to an empty list. If profile is omitted, it defaults to "debug".

Profile Resolution

The profiles map translates user-facing profile names to Zig-native optimization values:

profiles: {
    debug: {
        optimize: "Debug"
    }
    release: {
        optimize: "ReleaseFast"
    }
}

This indirection means you can add new profiles (e.g. "small" mapping to ReleaseSmall, or "safe" mapping to ReleaseSafe) without changing the project file format.

Adding a New Profile

  1. Add the value to the #Profile disjunction in schema.cue
  2. Add its optimization mapping to the profiles struct
  3. Use it in project.cue
// schema.cue
#Profile: "debug" | "release" | "small"

profiles: {
    debug:   { optimize: "Debug" }
    release: { optimize: "ReleaseFast" }
    small:   { optimize: "ReleaseSmall" }
}

Understanding CUE Syntax

If you're new to CUE, here are the key concepts used in the Azazel schema:

Definitions (# prefix)

Names starting with # are definitions — they define types but don't produce output. #Module is a type, not a value. You create values by unifying a definition with concrete data using &:

// #Module is the type definition
// app is a concrete value that satisfies the type
app: #Module & {
    kind: "exe"
    root: "src/main.zig"
}

Disjunctions (|)

The | operator creates a closed set of allowed values (like an enum in other languages):

#Kind: "exe" | "static" | "shared"

Any value assigned to a #Kind field must be exactly one of these three strings. Anything else is a validation error.

Defaults (*)

The * operator marks a preferred value in a disjunction:

profile: #Profile | *"debug"

This means: "profile must be a valid #Profile, and if not specified, defaults to "debug"." The default is applied during cue export — the user never sees incomplete values.

Open vs. closed lists

[...string] means "a list of zero or more strings." The ... makes it open-ended — any length is valid. Without ..., CUE would require an exact-length match.

Unification (&)

The & operator merges two values, checking that they're compatible. When you write #Module & { kind: "exe" }, CUE verifies that kind: "exe" satisfies the #Kind constraint, that root is still required, and that defaults for deps and profile are applied.

How the Export Pipeline Works

export.cue ties everything together. Here's the full flow:

// export.cue
_modules: {
    "core": core    // references the 'core' value from project.cue
    "app":  app     // references the 'app' value from project.cue
}

build: modules: {
    for k, v in _modules {
        (k): {
            kind:     v.kind
            root:     v.root
            deps:     v.deps
            optimize: profiles[v.profile].optimize
        }
    }
}

The for comprehension iterates over _modules, and for each module, it:

  1. Copies the kind, root, and deps fields directly
  2. Resolves profile through the profiles lookup table to get the Zig-native optimize value
  3. Produces a flat, fully-resolved struct with no remaining references or defaults

The _ prefix on _modules marks it as hidden — it won't appear in the exported output. Only the build struct is exported.
